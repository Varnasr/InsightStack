# KM_tools

Conventions for organising a project's files so that a location says what a
file is and a newcomer can find last year's endline without asking.

| File | What it is |
|---|---|
| `folder_structure_template.md` | One structure, numbered in workflow order, with the rules that make it hold: raw data never edited, every output generated by a script |
| `readme_template.md` | The two-page README a project folder starts with: people, where things are, codes, how to run the analysis |
| `file_naming_conventions.md` | `project_doctype_scope_version` and why |
| `tagging_structure_guidance.md` | Tag axes for a document store: theme, geography, stage, type, audience |
| `documentation_flowchart.pdf` | The path from draft to final for a brief, deck or report |

Two rules do most of the work. Raw data is never edited; anything wrong with
it is fixed by a script that writes somewhere else. And every table and
figure in a report was produced by a script that is still in the folder. A
project that keeps those two can be handed over, replicated
(`../replication/`), and audited. One that does not has a set of files that
only one person understands.
